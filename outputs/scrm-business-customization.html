SCRM 功能取舍与业务定制蓝图

2026-11-08 · 基于已完成的功能观察与用户业务说明 · 产品需求规划，不是实现完成清单

业务起点：Facebook 获客 → WhatsApp 客户运营，首批市场为美国和波多黎各。漏跟进、去重、翻译、团队协作、订单对接和归因均纳入设计。人数、账号数、渠道数不作为功能上限；具体商品作为可接入的业务目录，不作为这次需求梳理的前置。

我们借鉴现有产品中已观察到的业务能力，用自己的流程、数据模型和界面实现。现成出海猫账号能配置的内容，与自建系统需要新增的能力，应分别看待；普通使用账号不代表可以直接修改供应商的服务器或桌面客户端。

1. 先围绕业务结果组织系统

来源与广告 → WhatsApp会话 → 客户身份与分配 → 销售阶段与跟进 → 外部订单/履约 → 售后与复购 → 内部归因与经营复盘
业务流程具体路径必须处理的边界
B01 接入与首响Facebook来源 → WhatsApp接入 → 匹配/创建客户 → 分配负责人 → 回复或生成待办来源未知仍可接待；重复消息不重复建档；无人可接时进入队列
B02 线索到成交客户需求记录 → 可配置销售阶段 → 跟进任务 → 报价/外部订单 → 状态同步拒绝、无回复、客户转交、取消与退款要有路径；点击数不等于成交数
B03 售后与复购已完成订单 → 售后/问题处理 → 合适时机的联系任务 → 新订单或停止联系客户退订、投诉或问题未解决时停止相应自动化
B04 归因与复盘来源记录 + 会话 + 阶段变更 + 订单事实 → 内部经营报表 → 按授权决定外部回传无法匹配的来源、退款和重复事件独立处理；保留审计
B05 团队扩展创建组织/团队 → 邀请成员 → 分配角色和资源范围 → 配置队列/规则 → 审计人数和账号增加只调整资源/配额，不复制业务代码

流程中的市场、语言、阶段、规则、人员和资源均可配置。初始英语/西语不构成未来语言限制；对客户语言的判断以选择和实际沟通为准。外部平台是否允许某种接入和业务场景，在上线阶段独立核验，不靠软件界面保证。
