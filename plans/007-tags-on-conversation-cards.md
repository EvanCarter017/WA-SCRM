## Why this matters

The product owner asked on 2026-11-17:

> "Within the WhatsApp API chat interface, it should be possible to display tags directly on the customer card. It's fine if they aren't all fully visible, but at the very least, I should be able to get a general idea of the customer's status at a single glance."

Today the customer cards in the chat list of the WhatsApp API page (`#inbox`) show the name, the tier badge, the last message, the unread count, the account and the follow-up status. A customer's tags are visible only after opening the conversation (in the strip above the messages). After this plan each card also shows the customer's tags in one compact row: the first three, each cut off with an ellipsis if long, followed by "+N" for the rest; hovering shows the full list.

### Decisions already made (do not re-open; do not ask)

1. "Customer card" means a card in the conversation list on the left of the WhatsApp API page.
2. One row, never wrapping: at most three tags, then `+N`. Long tag names are cut off with an ellipsis. The full list is in the row's tooltip.
3. A customer without tags gets no row (the card keeps its current height).
4. Only tags the current viewer may see are shown — the same rule as everywhere else (`tagsHTML` already applies it).
5. Tags only. The tier badge is already on the card; nothing else is added.
6. The prototype still starts without any tags (an earlier owner decision: tags are fully user-defined and the system never creates them). The row therefore appears once tags have been created and assigned.
7. The version string stays `0.8-scrm-engagement`.

A zero-dependency, offline, clickable **prototype** of an internal WhatsApp customer workbench: plain HTML/CSS/JS, no framework, no package.json. All data is fictional demo data kept in the browser's `localStorage`. UI text is **Simplified Chinese**; write UI text exactly as given in this plan.

### How the build works

`work/wa-replica/build-fidelity.cjs` reads a frozen baseline app (`work/wa-replica/fidelity-base/app.js`), applies string substitutions with a `swap(from, to)` helper (**never change a first argument**), and concatenates the module files into the body of one IIFE. ### Helpers available in the shared scope (use them; do not redefine)

- `tagsHTML(c, max)` — returns the customer's first `max` visible tags as `<span class="tag COLOR">name</span>` chips, in the order of `c.tags`. It already hides tags the current viewer may not see. It returns an empty string when there are none.
- `myTags()` — all tags the current viewer may see (objects with `id`, `name`).
- `tag(id)` — the tag object for an id.
- `c.tags` — array of tag ids on a customer.
- `esc(text)`.

The same chips are used in the strip above an open conversation: `<span class="tag-row">${tagsHTML(c, 3)}</span>`.

```js
  // Tags on a conversation card: the first three the viewer may see, then a count of the rest.
  // The row never wraps; the full list is in its tooltip. A customer without tags gets no row.
  const LC_CARD_TAGS = 3;
  function lcConversationTags(c) {
    const visible = new Set(myTags().map(t => t.id));
    const names = c.tags.filter(id => visible.has(id)).map(id => tag(id).name);
    if (!names.length) return '';
    const more = names.length - LC_CARD_TAGS;
    return `<span class="conversation-tags" title="${esc('标签：' + names.join('、'))}">${tagsHTML(c, LC_CARD_TAGS)}${more > 0 ? `<span class="conversation-tags-more">+${more}</span>` : ''}</span>`;
  }
```
