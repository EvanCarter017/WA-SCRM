## Why this matters

The product owner asked on 2026-11-17 for a richer customer list:

> "The current customer list lacks sufficient detail. We need to either separate 'Customer List' and 'Customer Management' into distinct sections or integrate them into a single, comprehensive customer list. Specifically, implement a customer tiering system (D, C, B, A, and S grades), which can be manually assigned or adjusted within the chat interface."
>
> "The customer list should support filtering based on customer status — specifically: converted (closed deals), abandoned orders, and organic leads. This, too, can be managed by manually updating customer information within the chat interface."

Today a customer can only be classified with free-form tags, and the list shows neither a grade nor a commercial status. After this plan every customer has a manual **tier** and a manual **status**; an agent sets both without leaving the chat; and the single customer list shows them, filters by them, and exports them.

### Decisions already made (do not re-open; do not ask)

The owner does not review plans and has delegated open points to the advisor:

1. **One comprehensive customer list**, not two pages. The owner offered either option; a second "customer management" page would duplicate the list. The navigation stays as it is.
2. **Tier**: exactly `S`, `A`, `B`, `C`, `D` (S is the highest). A customer starts **unrated** (`未评级`). The system never assigns or changes a tier on its own.
3. **Status**: one value per customer, chosen from `已成交` (converted), `弃单` (abandoned order), `自然线索` (organic lead). A customer starts **unmarked** (`未标记`). The system never assigns or changes a status on its own.
4. Both are edited with two small drop-downs that save immediately, shown in the **chat strip** (above the conversation) and in the **customer dossier** header. Each change is written to the customer's activity log.
5. Tags stay exactly as they are (free-form, user-defined).
6. The version string stays `0.8-scrm-engagement`.

### What this repository is

A zero-dependency, offline, clickable **prototype** of an internal WhatsApp customer workbench: plain HTML/CSS/JS, no framework, no package.json. ### How the build works

`work/wa-replica/build-fidelity.cjs` reads a frozen baseline app (`work/wa-replica/fidelity-base/app.js`), applies string substitutions with a `swap(from, to)` helper (which asserts `from` exists — never change a first argument), and concatenates the module files into the body of one IIFE in this order: `fidelity-ui.js`, `fidelity-customer-pages.js`, `fidelity-operations.js`, `fidelity-openwa.js`, `fidelity-dashboard.js`, `fidelity-lifecycle.js`, `fidelity-subsite.js`. All files share one scope: a later file overrides an earlier definition by re-assigning it, and can call any helper from an earlier file. It writes `outputs/wa-replica-prototype/*` and two identical standalone bundles, `outputs/whatsapp-scrm-lifecycle.html` and `outputs/whatsapp-replica-ui-fidelity.html`. **Outputs are committed and must be regenerated by running the build, never edited by hand.** CSS is built from `fidelity-base/app.css` + `fidelity.css` + `fidelity-dashboard.css` + `fidelity-lifecycle.css` (later files win on equal specificity).

Icons: the build takes icon definitions from the existing `outputs/wa-replica-prototype/icons.js` and writes back only the icons still referenced. Restore that file from git before every build (command below). **This plan needs no new icons; do not introduce any.**
