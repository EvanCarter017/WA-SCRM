## Why this matters

On 2026-11-22 the owner's page read the 87 chats the server had fetched from WhatsApp and tried to save them: one request of about 290 KB. A proxy in front of the server allowed 64 KB and answered "413 Request Entity Too Large". The page showed "修改暂未保存到服务器，正在重试…" and tried again and again with the same request; nothing was saved until an administrator raised the proxy's limit by hand. The same dead end exists without any proxy: the server itself takes at most 8 MB in one request, and the first save after linking a number with many chats can be larger than that.

This plan closes that:

- **A large change is sent in parts.** One save request carries at most about 256 KB of values (a single value that is larger goes alone). What does not fit follows in the next request, at once.
- **The order makes an interrupted save harmless.** Whole fields (customers, to-dos, …) go first, then the per-customer entries (conversations, history), and the position in the WhatsApp feed last. If the page is closed between two parts, the next page reads the feed again from the position that was saved and fills in what is missing.
- **A refusal for size says so.** On the answer 413 the notice reads "修改未能保存：内容超过服务器允许的大小，请联系管理员。" instead of "正在重试…". The page still tries again (slowly, as before), so the save goes through once the limit has been raised.
- **The README names the limit a proxy needs.**

### Decisions already made (do not re-open; do not ask)

- The part size is 256 × 1024 characters, so that the usual request passes a proxy with a 1 MB limit.
- The page keeps retrying after a 413 (it did go through on its own once the limit was raised); only the notice changes.
- The server, its limits (8 MB a request, 2 MB a value) and its tests are not changed.
