## Why this matters

The product owner asked on 2026-11-17:

> "The 'Chat History' sub-section — part of the customer and follow-up management workflow — needs to be overhauled. It should pull from the aggregate chat logs provided by the WhatsApp API, allowing users to move specific customer conversations into this section for the purpose of performance review and auditing."

Today the chat-history page (`#chat-records`, "聊天记录") is a second browser over **every** live conversation (pick an account, pick a contact, read the messages). It duplicates the inbox and has no review purpose. After this plan it is a **review archive**: it contains only conversations that someone deliberately moved in from the WhatsApp chat, each stored as a frozen snapshot with who moved it, when and why, and each can be given a review result and a comment.

### Decisions already made (do not re-open; do not ask)

The owner does not review plans and has delegated open points to the advisor:

1. **"Move" means snapshot.** Moving a conversation in copies its messages as they are at that moment. The live conversation stays in the inbox and is not changed, so the agent can keep talking to the customer.
2. The page shows **only** moved-in snapshots. The old account → contact browser is removed.
3. A **reason** is required when moving a conversation in.
4. A snapshot has a **review result**: `待质检` (not reviewed yet, the default), `合格` (pass) or `需改进` (needs improvement), plus a free-text comment. A comment is required for `需改进`. In the real product a supervisor reviews on the main site; in this prototype the review controls are usable by the current viewer so the flow can be evaluated — say so in the UI.
5. A customer can have several snapshots (taken at different times). The only duplicate that is refused is moving in a conversation whose current content is already archived and still waiting for review.
6. An agent sees the snapshots of their own customers (`manager()` sees all), the same visibility rule as the rest of the prototype.
7. Two demo snapshots are written once per browser so the page is not empty on first visit.
8. The existing "聊天翻译" switch on this page stays.
9. The version string stays `0.8-scrm-engagement`.

### How the build works

`work/wa-replica/build-fidelity.cjs` reads a frozen baseline app (`work/wa-replica/fidelity-base/app.js`), applies string substitutions with a `swap(from, to)` helper (which asserts `from` exists — never change a first argument), and concatenates the module files into the body of one IIFE in this order: `fidelity-ui.js`, `fidelity-customer-pages.js`, `fidelity-operations.js`, `fidelity-openwa.js`, `fidelity-dashboard.js`, `fidelity-lifecycle.js`, `fidelity-subsite.js`. All files share one scope. A function declared with `function name() {}` in any of them can be called from any other at run time; a `const` helper can be used by code that runs after it is defined (all page rendering and all click/submit handlers run after every file has loaded). It writes `outputs/wa-replica-prototype/*` and two identical standalone bundles, `outputs/whatsapp-scrm-lifecycle.html` and `outputs/whatsapp-replica-ui-fidelity.html`. **Outputs are committed and must be regenerated by running the build, never edited by hand.**

Icons: the build takes icon definitions from the existing `outputs/wa-replica-prototype/icons.js` and writes back only the icons still referenced. Restore that file from git before every build (command below). **Use only icons that this plan's code blocks already use; do not introduce others.**
